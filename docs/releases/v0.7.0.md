# Gigworkers v0.7.0 – Gig Worker Unique ID and Multiple Aggregators

**Release date:** 2026-08-24 · **Release type:** Minor · **Previous version:** v0.6.0

## Summary

Every gig worker now gets a unique ID generated from their ID proof, and a worker who works for
several platforms can be linked to all of their aggregators under that one ID.

## Highlights

- **Automatic Gig Worker Unique ID** generation.
- **One worker, many aggregators:** each worker can hold a partner ID with each aggregator.
- ID-proof fields used in the unique ID become **mandatory**.

## Changes by module

### Gig Worker Management
- A unique ID is generated for each new worker using the rules in **Gig Worker Unique ID
  Settings**. Its running number is reserved safely, so two workers never receive the same ID.
- Any ID-proof field used to build the unique ID (PAN, Driving Licence or Aadhaar) becomes
  mandatory on the gig worker form.
- Aadhaar numbers are always displayed with only the last 4 digits visible.

### Worker Partner Mapping
- Each worker now has **one** mapping record, with a table of aggregators. Each row holds the
  aggregator, partner ID, mapping date and status.
- A worker can be linked to each aggregator only once.

### Bulk Import and Import Logs
- The gig worker import can link a worker to several aggregators and partner IDs.

## Security

- Import pages check the user's role on the server. Users can only follow the progress of import
  jobs they started themselves, except administrators.

## Technical changes

- New child DocType: Worker Aggregator Detail.
- New patches: `snapshot_worker_partner_mapping_before_restructure` (pre-model-sync) and
  `migrate_worker_partner_mapping_to_child_table` (post-model-sync).

## Breaking changes

| Change | Action required |
|---|---|
| Worker Partner Mapping changed from one record per worker–aggregator pair to one record per worker with an aggregator table | Existing data is migrated by the patches. Update any custom reports or scripts that read the old fields |

## Upgrade instructions

```bash
bench --site <site> backup --with-files
cd apps/gigworkers && git fetch --tags && git checkout v0.7.0 && cd ../..
bench --site <site> migrate
bench build --app gigworkers
bench --site <site> clear-cache
bench restart
```

`migrate` runs two patches. The first copies the existing worker–aggregator mappings aside before
the schema changes. The second rebuilds them in the new one-record-per-worker structure and then
removes the temporary copy. **Take a backup first.**

After upgrading, open a few **Worker Partner Mapping** records and check that every aggregator and
partner ID is present.
